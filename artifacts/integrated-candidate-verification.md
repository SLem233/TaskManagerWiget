# Проверка интегрированного APK-кандидата

Дата: 2026-10-01. Источник: `app/build/outputs/apk/debug/app-debug.apk`; сохранённая копия: `artifacts/taskmanager-widget-candidate.apk`.

## Реализовано

Виджет читает локальный индекс Vault, показывает agenda и позволяет завершать задачу из строки. `TaskWriter` проверяет неизменность Markdown и результат записи, SQLite-журнал предоставляет Undo и recovery-копии. После записи или Undo индекс перепарсивает только затронутую заметку, сохраняя соседние задачи. Refresh и периодическое обновление используют `JobScheduler`; настройки вида привязаны к `appWidgetId`, текст задачи открывает заметку через `obsidian://open`.

## Автоматические проверки текущего APK

- `python -m unittest discover -s scripts -p 'test_*.py'`: 4 теста, 0 ошибок.
- `gradlew.bat testDebugUnitTest createDebugUnitTestCoverageReport assembleDebug lintDebug`: 92 Android/JVM теста, 0 failures/errors/skipped; сборка успешна, lint: 0 errors, 22 warnings.
- JaCoCo по всему приложению: 927/1141 строк = 81,2%; требование ≥80% выполнено. Отчёт: `app/build/reports/coverage/test/debug/index.html`.
- Все 41 Kotlin-файл в `app/src` имеют не более 500 строк.
- APK: versionCode 6, versionName `0.4.0-integrated-candidate`, minSdk 26, targetSdk 36; SHA-256 исходника и сохранённой копии совпал: `9E7B75ABA4A57304EE726E4D62CB5BA7C18698C322F3DECCEE25170807994867`.
- `aapt dump permissions` не вывел Android-разрешений, включая INTERNET.
- API 36 тесты на Windows используют тестовый `WindowsAtomicFileShadow` для замены существующего файла. Production `AtomicFile` и APK не меняются этим shadow.

## Проверка на Realme/Android 16

`adb devices -l` показал Realme `RMX5303` со статусом `device`, API 36. `adb install -r` текущего APK вернул `Success`; пакет сохранил versionCode 6 и versionName `0.4.0-integrated-candidate`. `MainActivity` запускалась, процесс работал; в проверенном окне `AndroidRuntime:E` падений не было. `dumpsys appwidget` показал экземпляр виджета `id=17` у `com.android.launcher3`.

Владелец подтвердил: после исправления отметка одной задачи в заметке оставляет соседнюю видимой, Undo возвращает выбранную; Markdown меняет только выбранную строку. Также проверены открытие заметки нажатием на текст, прокрутка и изменение размера виджета, Refresh после внешней правки и сохранение доступа к Vault после перезапуска.

Владелец предоставил два снимка: `widget-realme-large-2026-10-01.jpg` и `widget-realme-compact-2026-10-01.jpg` (хранятся только в локальном `artifacts/` из-за реальных названий задач). JPEG скопированы без обработки, SHA-256 копий совпал с исходниками. На большом снимке видны несколько групп дат и задач, на компактном — часть прокручиваемого списка. Снимки сделаны до индикации Refresh.

Владелец принял текущий кандидат и разрешил коммит и push. Отдельного результата визуальной оценки цветов и таймера, а также аппаратных сценариев повторения и конфликта не получено. Самостоятельное периодическое срабатывание и чистая установка не подтверждены. Сценарий: [TESTING.md](../TESTING.md).

## Дефект двух задач в одной заметке

Владелец обнаружил: после отметки одной задачи обе задачи того же дня исчезали из виджета и обе возвращались после Undo, хотя в Markdown изменялась только одна строка. Причина: `VaultRepository.complete` и `undo` удаляли из индекса весь документ. До исправления интеграционный тест с двумя задачами в одном SAF-документе падал на отсутствии второй. После исправления тест и полный suite прошли на API 26/28/36: на том этапе 77 Android/JVM тестов, 4 Python теста и покрытие 869/1072 строк (81,1%). Владелец подтвердил исправление на Realme.

## Индикация Refresh

После запроса владельца добавлена строка под заголовком: `Обновляю...` сразу после авторизованного нажатия, `Обновлено` или `Ошибка обновления` после фонового сканирования. Тест до реализации падал из-за отсутствия статуса; после реализации проверены немедленная обратная связь, результат и истечение зависшего состояния на API 28/36. Текущий полный suite и APK приведены выше. Владелец принял текущий кандидат; отдельного наблюдения этой строки на постоянно включённом экране не зафиксировано.

## Таймер, цвета и фоновое задание

После сообщения владельца о залипшем `Обновлено` добавлен красный регрессионный тест автоматической перерисовки через 5 секунд. Состояние успеха теперь истекает по монотонным часам Android с календарным временем как резервом после сна/перезагрузки; Handler перерисовывает виджет. Тест прошёл на API 28/36. На Realme после нажатия Refresh UI показывал `Обновляю...` на ~3,7 с и `Обновлено` на ~6,6 и ~9,4 с. Затем экран уснул; сохранённое состояние стало `IDLE`, но визуальное исчезновение при постоянно включённом экране ещё ожидает подтверждения владельца.

По согласованному правилу цвет названия задачи: до Start — белый `#FFFFFF`, с Start — синий `#0080FF`, с Scheduled — жёлтый `#FFFF80`, в день Due — оранжевый `#FF8040`, после Due — красный `#FF0000`. Более срочная дата имеет приоритет. Чистые тесты проверили все пять состояний и пересечения; Android-тест проверил реальный цвет TextView в RemoteViews. Владелец принял текущий кандидат; отдельный отзыв о каждом цвете не получен.

На Realme `cmd jobscheduler get-job-state ru.slem.taskwidget 4102` показал `waiting`. Принудительный запуск `cmd jobscheduler run -f ru.slem.taskwidget 4102` вернул `Running job [FORCED]`. Через ~5 с mtime локального `task-index-v1.bin` изменилось с `1790847811` на `1790847933`, состояние задания вернулось в `waiting`. Это подтверждает выполнение фонового сканирования; самостоятельное срабатывание по расписанию ещё не наблюдалось.

После добавления SAF интеграционных тестов повторения/Undo и конфликта полный suite прошёл: 92 Android/JVM и 4 Python теста, покрытие 927/1141 строк (81,2%), lint без ошибок. APK не изменился после добавления тестов: SHA-256 `9E7B75ABA4A57304EE726E4D62CB5BA7C18698C322F3DECCEE25170807994867`; `adb install -r` на Realme вернул `Success`. Синтетические SAF-тесты прошли на API 26/28/36 и не заменяют ручную приёмку этих действий на устройстве.

## Git и первый коммит

`subagent-workflow` 0.2.2 не поддерживает связь telemetry с первым коммитом без `HEAD`. Для сохранения защитного hook сначала создаётся пустой bootstrap-коммит через отдельный пустой Git index; основной staged index при этом не меняется. Следующий коммит с файлами связывается с точным `model_run` обычным `finish --commit`.
