# План разработки Android-виджета задач Obsidian

Дата: 2026-10-01. Статус: этап 3 принят владельцем; APK-кандидат этапов 4–6 принят владельцем для коммита и push после проверки на Realme. Общее покрытие 81,2%. Чистая установка и сохранение SAF-доступа после reboot проверены; persisted job остался в системе после reboot. Точный автономный 30-минутный интервал не измерялся.
Источники: `TZ_Obsidian_Tasks_Android_Widget.md` из Downloads, ответы владельца в этой беседе, `TZ-review-2026-09-30.md`, `references/calendar-reference.jpg`.

## Цель и границы MVP

Один Android home-screen widget для локального Obsidian Vault. Он показывает активные задачи с выбранным тегом (по умолчанию `#task`) на 14 дней вперёд, позволяет прокручивать список, отмечать выполнение, обновлять данные и открывать заметку в Obsidian. Размер меняется средствами launcher. Приложение содержит выбор папки Vault, настройку тега, шрифта и прозрачности, журнал операций с отменой. Нет отдельного менеджера задач, облачного сервера, аккаунта и синхронизации: GitHub-синхронизацию Vault выполняет уже установленный пользовательский механизм.

Визуальный образец — `references/calendar-reference.jpg`: прозрачный фон без карточки, компактные строки, белый основной и серый вторичный текст, даты между группами. Цветные блоки времени заменяются checkbox. Приёмочное устройство — Realme с Android 16; минимальная версия Android 8/API 26 остаётся требованием исходного ТЗ, если владелец её явно не изменит. Проверки на одном Realme не дают оснований заявлять совместимость со всеми launcher.

Поддержка Tasks означает совместимость с его настройками по умолчанию, включая встроенные `[ ]` и `[x]`, добавляемые Tasks `[/]` и `[-]`, стандартные поля дат, приоритета, даты завершения и повторения. Точные преобразования статусов и повторений сначала фиксируются по документации Tasks и проверяются на тестовых заметках в целевом Obsidian. Приложение не должно самостоятельно менять поведение, зависящее от настроек плагина, на основании догадки.

## Решения по данным и датам

- Обрабатывать только Markdown checkbox со **строго отдельным тегом**, указанным в настройках; исходное значение `#task`. Строки обычных checklist игнорировать.
- Дата группы: Scheduled, иначе Due, иначе Start, иначе «Без даты». Будущие задачи видны заранее, даже если Start ещё не наступил. Задача только со Start в прошлом остаётся в «Сегодня»; её дата в Markdown не меняется.
- «Без даты» включена по умолчанию и видна после датированных групп. Горизонт 14 дней применяется к будущим датированным группам; просроченные и «Без даты» остаются доступны независимо от горизонта.
- Невыполненная задача попадает в «Просрочено» только если указан Due и он раньше сегодня. Прошедший Scheduled сам по себе не делает задачу просроченной. Если Scheduled прошёл, а Due ещё не наступил или отсутствует, задача отображается в «Сегодня» без изменения Markdown. Задача только со Start в прошлом также отображается в «Сегодня».
- Приоритеты реализовать по фактическому синтаксису Tasks, включая Medium и отсутствие приоритета. Исходная таблица ТЗ с `⏫` как Highest требует сверки с актуальной документацией Tasks. Сортировка внутри группы: приоритет, ближайший Due, стабильный порядок по файлу и строке.
- Статусы done/cancelled не показываются как активные; точное поведение in-progress и нажатия checkbox определить по состоянию Tasks по умолчанию. Неподдерживаемый синтаксис или правило повторения не должен приводить к частичной записи файла.

Механическую обработку большого Vault выполнять кодом и скриптами; спорные случаи сохранять в отдельном отчёте, не решать вручную строка за строкой.

## Контроль каждой фазы

После реализации очередной фазы: полный подходящий прогон тестов → ручная приёмка владельцем → обновление русской документации → коммит последним шагом. Владелец отдельно разрешил продолжить разработку до итогового кандидата без промежуточных остановок; итоговая аппаратная приёмка версии 6 ещё ожидается. До неё коммит не делать. Для фазы прототипа ручная приёмка включает реальный launcher. Если у разработчика нет доступа к Realme, фаза 1 остаётся кандидатом и ожидает фактической проверки владельцем, без заявления об успешной аппаратной проверке.

При начале постоянной работы и создании проекта выполнить регистрацию в AgentPulse по глобальному AGENTS.md. Если позже будет запущена реализация по `subagent-workflow`, до кода провести preflight, оформить GitHub Project/Issues и назначения моделей, затем вести телеметрию run. План сам по себе не запускает этот цикл.

## Открытые решения и критерии начала

1. **Просроченный Scheduled при ещё не наступившем Due.** Ранний ответ: «Просрочено». Последний: «в просроченные уезжает только после дедлайна». Нужен явный выбор владельца; до него этап группировки не начинать.
2. Для повторений проверить стандартные правила Tasks в конкретной установленной версии и синтетические примеры. Если формат в реальном Vault окажется иным, обновить контракт тестов до writer.
2. Уточнить точность горизонта: сегодня плюс 13 или плюс 14 календарных дней. Предложение: сегодня и следующие 13 дней включительно.
3. Журнал: предложение хранить последние 100 операций до ручной очистки; при конфликте Undo отказаться от записи и предложить открыть заметку. Это проектное предположение, не решение владельца.
4. Сопоставление внешних изменений GitHub-синхронизации с индексом и Undo проверить на устройстве: статус успеха определяется содержимым Markdown после действия, а не только успешным запуском фонового обновления.

План реализуется по этапам. На 2026-10-01 APK-кандидат этапов 4–6 собран, 94 Android/JVM и 4 Python теста прошли, покрытие 81,2%. Владелец принял текущий APK на Realme и разрешил коммит и push; чистая установка и сохранение SAF-доступа после reboot проверены; persisted job пережил reboot и выполнил сканирование после него. Точный автономный 30-минутный интервал не измерялся. Подробности — artifacts/integrated-candidate-verification.md. Ранее принятые этапы 0–3 описаны в docs/PHASES-0-3.md.
